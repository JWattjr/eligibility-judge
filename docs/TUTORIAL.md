# Build an evidence-backed qualification challenge

Eligibility Judge is a small application with a deliberately narrow consensus boundary. The browser helps users prepare submissions and inspect results. It does not decide whether a project qualifies. That decision belongs to the Python Intelligent Contract in `contracts/eligibility_judge.py`, executed by GenLayer validators. This tutorial follows the actual methods and data in this repository.

Start by installing the dependencies in the README and running `npm run dev`. The application opens the retained demonstration challenge without connecting a wallet. Choose Recorded proof to inspect the version saved in `deploy/proof.json`; choose Live chain to fetch the contract's finalized state. These are different sources, so the interface labels both. A cached record is useful for a reliable walkthrough, while live reads establish what the contract currently stores.

To publish your own challenge, connect an Ethereum wallet on StudioNet, chain 61999. Open Create challenge and supply a title, a brief, three to six eligibility rules, opening and closing times, entry capacity, and a prize pool. The form calls the contract's payable `create` method. Amounts are converted to integer wei; the contract stores amounts as decimal strings when exposing JSON to JavaScript, preventing rounding of large integers. The contract accepts positive funding up to 1000 StudioNet GEN and at most twenty entries. The browser wallet adapter pins an explicit legacy gas price before forwarding SDK transaction requests to the wallet, matching the CLI fee configuration. Wallet confirmation remains required.

Choose rules that can be checked from the public repository or an archived page. “README contains deployment instructions” is a good example. “Well designed” is not objectively checkable. After creation finalizes, the app requests a separate wallet signature for each rule validation in sequence. If a signature is declined, continue manually from Rulebook. Each `validate_rule` transaction asks validators one question: is this rule objective and observable? The leader's result must contain a boolean and a reason. Other validators independently answer and compare the boolean. Accepted rule transactions schedule `finalize_rule` as a native finalized callback. Only self-sent callbacks can change the recorded rule checks. When every check is present, the contract either rejects the rulebook or freezes it by storing a SHA-256 hash of the ordered rule list.

Builders then submit through Submit entry. Paste a public GitHub URL and choose Preview evidence. The server resolves HEAD to a full forty-character commit SHA and retrieves the repository tree. You may instead paste a known SHA. The preview uses the same capped file ordering as the contract: metadata first, contract and test files next (including Python, TypeScript, and other supported code formats), followed by other eligible text files. Previewing does not grant eligibility and does not prove that validators can fetch the content. Each validator fetches its own pinned sources during judgment. Optional demo evidence must be a dated archive.org snapshot URL, preserving an observable historical version.

The `enter` method enforces the opening window, GitHub authority, SHA format, capacity, and one entry per address. Once an entry is stored, anyone may call `judge_rule` for each rule. The transaction judges precisely one rule against precisely one entry. `fetch_evidence` fetches the GitHub tree at the pinned SHA and at most ten selected raw files from raw.githubusercontent.com. It retains at most 96,000 tree bytes and 12,000 bytes per file. Unavailable or oversized evidence stays explicit rather than being silently treated as proof of failure.

The model returns a fixed object: status, path, quote, and reason. Status must be PASS, FAIL, or INSUFFICIENT_EVIDENCE. PASS and FAIL require a nonempty verbatim quote appearing in a fetched source. The contract verifies the complete model quote before storing at most 600 characters, so a valid longer excerpt can finalize without allowing a fabricated suffix to disappear behind the storage cap. `check_answer` rejects nonexistent quotes and judge-directed instructions presented as positive evidence. The custom validator fetches independently, checks the leader's citation against its own content, compares evidence fingerprints, independently derives the verdict, and verifies that the proposed quotation supports that verdict. Comparing only PASS or FAIL would leave the citation unverified, so this implementation does more.

The transaction's finality callback stores each verified verdict. Once every rule has a finalized result, deterministic code derives the overall outcome. Every rule passing means QUALIFIED. At least one failure means DISQUALIFIED. Otherwise the entry is INSUFFICIENT_EVIDENCE. A failed or inconclusive entrant may submit one new commit before the window closes. The contract keeps the previous attempt in history and prohibits further revisions. A qualified entrant cannot replace its successful commit.

After close, call `settle`. It refuses to run while any entry still lacks finalized judgments. Deterministic integer division calculates each qualifier's share and the remainder refunded to the organizer. If nobody qualifies, the entire pool becomes a refund. Settlement itself waits for a finalized callback before claims open. `claim` records a wallet's claim once and emits a native GEN transfer. A successful claim request is not sufficient proof of delivery: the live release script verifies the emitted transfer's finalized value credit, exact amount, and recipient. `claim_refund` separately authorizes the organizer's refund.

Transaction hashes are saved locally in the browser so a reload does not lose progress. A successful leader execution with MAJORITY_DISAGREE is a failed transaction: agreement and finalized callbacks are required before the app reports success. Accepted transactions remain provisional during GenLayer's native appeal window; the UI queries native appeal availability rather than inventing a timer. The transaction trail can initiate a native appeal with the protocol's required bond. There is no custom court.

Before presenting the project, run the direct tests, GenVM lint, TypeScript typecheck, production build, and read-only proof verifier. Direct tests are fast and cover adversarial inputs and accounting, but they do not execute the real validator path or native transfers. The live manifest and receipt checks are therefore essential. Consult `docs/DEMO.md` for the short walkthrough and `docs/submission/portal-fields.json` for the human submission fields.


## Exact metadata and bounded content

A live regression returned an entire reconstructed GitHub tree object as a quote, attributed to a test file. The file was real, but that JSON was not its contents. The release now accepts that form only when every metadata field matches a fetched tree node. It then stores the actual filename as a verbatim quote in `__TREE__`. Validators independently fetch and validate the same tree and separately confirm that the citation supports the rule. A changed SHA, size, path, extra instruction field or fabricated suffix is rejected. This is evidence normalization, not acceptance of the model's unsupported citation.

The README regression also showed why file truncation matters. A model sometimes called an incomplete README a failure and another called it insufficient evidence. The release conservatively converts failures citing a truncated file into insufficient evidence. Positive evidence already visible in a prefix may still pass. A completed entry with another failing rule remains disqualified.

Before another funded demonstration, six zero-value calls used the same adjudication helpers in a consensus-only probe. Each finalized with validator agreement. `npm run verify:smoke` independently checks those receipts, stored samples, exact deployed source and helper identity. The probe has no pool or payout methods. A large SDK repository returned insufficient evidence for the Python-contract rule; this result is preserved, including the initial expected failure. A small, fully inspected control branch conclusively failed that rule and serves as the ordinary negative demo entry. The original injection branch remains unchanged. The complete funded demonstration remains a separate requirement checked by `npm run verify:proof`.
